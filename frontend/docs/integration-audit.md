# Integration audit — 25 October 2026

This audit compares the current React forms/API client with backend routes, Zod validators, services, serializers, OpenAPI and state machines before integration changes. The existing orange/cream design remains approved. All HTTP paths below are under `/api`; JSON responses use `{ success, data }`, errors use `{ success:false, error:{code,message,details?} }`. Public means no bearer token; other actions check live account/session status and the indicated role on the server.

## Initial live environment findings

- The existing API answers `/ready` with 200. Atlas is connected to a replica set. Initial counts: zero administrator accounts, zero categories, zero professional profiles.
- Browser requests from `http://localhost:5173` succeed. The same requests from `http://127.0.0.1:5173` fail because the configured exact CORS origin is localhost. The current Vite command advertises the other hostname. Fix development navigation/configuration, not backend CORS.
- `MEDIA_PROVIDER=cloudinary` and the three credentials are present, but a real authenticated provider request returns 401 `api_secret mismatch`. A matching key/secret pair must be corrected in the local backend environment. No credential values were printed or copied to the frontend.
- Frontend `.env` is absent; its centralized client correctly defaults to `http://localhost:5000/api`. Add an explicit public-only local configuration and diagnostics.
- Existing test startup is timing out in mongodb-memory-server's 10-second Windows process-launch window before assertions run. Increase test-only startup allowance while retaining every existing assertion; never use Atlas as a replacement test database.

## Forms and endpoint contracts

`!` indicates a required request field. Optional fields are omitted when not collected. ObjectIds are server-validated references. Monetary values are nonnegative safe integer **bututs**, converted centrally from decimal GMD. All scheduling controls explicitly use Africa/Banjul; actual interval timestamps are UTC.

## Preserved boundaries

No frontend marketplace mock data, Cloudinary secrets, public administrator-registration route, unrestricted CORS or new real payment provider will be introduced. Initial admin provisioning follows the documented trusted local operator setup; catalog seeding uses authenticated catalog APIs. All jobs, quotes, bookings, messages, payments, ledger events, completion and reviews must be created by their real API workflows. Test fixtures remain isolated. Memory-only browser tokens and current logout/revocation policy remain intact; persistent reload sign-in would require a separately designed secure transport, not localStorage.

## Validation plan

1. Correct the localhost development entry point and verify both browser-hostname cases.
2. Provision dedicated local test credentials without printing or committing passwords; initialize catalog via ADMIN API.
3. Verify real media after the operator corrects the Cloudinary key/secret pair.
4. Run both customer and worker UI workflows, a real ADMIN review, realtime text/image/voice, simulated checkout and time-valid completion/review against the running Atlas-backed API. Wait for the actual scheduled start; never edit booking dates/statuses in the database.
5. Inspect only read-only persisted counts/references and authorized provider retrieval for evidence. Retain scoped demo resources for the user's manual FYP run.
6. Run backend/frontend tests, lint, production build, and isolated browser regression checks. Record live-provider results separately from fake-provider automated test evidence.
